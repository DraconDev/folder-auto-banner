# Goal Prompt

Make `install.sh` delegate the shell-wrapper setup to `f install` (which reads the corrected embedded `ZSH_WRAPPER` / `BASH_WRAPPER` from `src/shell_wrapper.rs`), so new users get a working `f N` → `cd` setup on first install with no risk of stale repo files being copied.

## Why
The standalone `fab-shell.zsh` and `fab-shell.bash` in the repo root are hand-maintained duplicates of the embedded strings in `src/shell_wrapper.rs`. They drift out of sync — `fab-shell.zsh` still uses `${args[0]}` (empty in zsh, which is 1-indexed) so a new user running `install.sh` gets a broken `f N` → `cd` because install.sh does `cp fab-shell.zsh "$BIN_DIR/"` (install.sh:126) and the matching `cp fab-shell.bash` at line 141. The bash file happens to be correct, but the zsh file is not. Even if we hand-fix the file in-repo, it will drift again next time someone edits the embedded wrapper.

`f install` is the correct, single-source-of-truth installer for the shell function: it reads from `src/shell_wrapper.rs` at compile time, writes the corrected wrappers to `~/.local/bin/`, and adds the source line to `~/.zshrc` / `~/.bashrc` (with idempotency check). Having `install.sh` call `f install` eliminates the duplication and the drift.

## Success criteria
1. `install.sh` no longer does `cp fab-shell.zsh` / `cp fab-shell.bash` — the manual copy lines are removed.
2. `install.sh` no longer writes the `# fab shell function (enables f N to cd)` block and its `source ...` lines to `.zshrc` / `.bashrc` — instead it calls `"$BIN_PATH" install` (or `target/release/f install` before the binary is copied) after the build step.
3. After running `install.sh` (or the equivalent new section in a scratch test), `~/.local/bin/fab-shell.zsh` contains `${args[1]}` / `${args[2]}` (1-indexed, zsh-correct) — not `${args[0]}`.
4. The chpwd-hook / PROMPT_COMMAND section (auto-banner on cd) is preserved as-is — that's a separate feature and not the shell function.
5. The cleanup sed commands in `install.sh` (lines 91-104) that remove old hook fragments are preserved — they handle variants that `f install` doesn't know about.
6. Build clean, `cargo test --lib` 0 failures, `install.sh` shellcheck-clean (or at least no new warnings), change committed and pushed to `main`.

## Boundaries
**In scope:** Editing `install.sh` to delegate wrapper setup to `f install`. May also touch `src/cmd/install.rs` to make the delegation ergonomic (e.g., add a `--quiet` flag or document the `install` subcommand). Not touching `fab-shell.zsh` / `fab-shell.bash` files in the repo root — those become effectively dead code, but cleaning them up is a separate concern (they're harmless to leave; `f install` overwrites them on first run).

**Out of scope:** Deleting or hand-fixing the standalone `fab-shell.zsh` / `fab-shell.bash` in the repo root. Changing the chpwd-hook / PROMPT_COMMAND behavior. Changing the systemd service install. Refactoring the PATH-add logic. Touching the daemon-start logic. Any unrelated cleanup.

## Constraints
- The `install.sh` script must remain idempotent — re-running it on an already-set-up system must not break anything.
- The chpwd hook section must continue to be added (it's a separate feature).
- The order of operations must remain: build → copy binaries → set up shell function → start daemon. The shell-function setup happens AFTER the binary is in place (so `f install` is callable).
- No new dependencies. No new system requirements. No breaking of the existing `--user` systemd path.
- If `f install` returns non-zero (e.g., write fails), `install.sh` should propagate the error (current `set -euo pipefail` should handle this).
- The delegation must work even on a fresh system where the user's `~/.local/bin` is not yet in PATH — `install.sh` should call `f install` via the just-copied absolute path (`"$BIN_PATH" install`), not via `f install`.
